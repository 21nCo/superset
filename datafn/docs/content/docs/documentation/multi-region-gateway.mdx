# Multi-region gateway routing

DataFn supports an opt-in canonical-gateway model for applications that keep each tenant namespace in one writable regional cell. Clients keep one `remote` and `wsUrl`; regional destinations remain internal deployment handles.

This capability does not provide active-active writes or automatic failover to an empty region. Existing single-region configurations and permission-directory grant indexing are unchanged unless a placement runtime is configured.

## Separate ownership from permission projections

`DatafnPlacementDirectoryAdapter` is the authority for namespace ownership. Its records contain a namespace, owning `regionId`, monotonically increasing `epoch`, lifecycle state, update time, and optional cache/destination metadata. `get`, `putIfAbsent`, and `compareAndSet` must all be linearizable for a namespace; for DynamoDB-backed atomic KV stores, configure strong reads (`consistentRead: true`).

The indexed permission directory is a separate projection. Permission-directory lag can affect sharing discovery, but it never changes a namespace's database owner. Migration must drain its outbox and rebuild the target projection explicitly.

The built-in `createConditionalKvDatafnPlacementDirectory` composes the focused placement contract with any `ConditionalKVStoreAdapter` that implements `compareAndSet`. Its required `consistencyModel: "linearizable"` acknowledgement makes the deployment contract explicit: DynamoDB adapters must enable `consistentRead: true`, and other providers must route reads and CAS writes through one linearizable authority. Memory, Redis, and Cloudflare Durable Object stores can use the same contract without placing provider APIs in DataFn core.

`createMemoryDatafnPlacementDirectory` is for tests and one-process deployments only. Migrations that must recover after a process crash require a durable placement directory so recovery ownership, fencing tokens, and lease state survive the restart.

## Regional cell

```ts
import {
  createConditionalKvDatafnPlacementDirectory,
  createDatafnHmacRoutingAssertions,
  createMemoryDatafnRoutingReplayStore,
  createDatafnServer,
  datafnMultiRegionPlugin,
} from "@datafn/server";

const assertions = createDatafnHmacRoutingAssertions({
  activeKeyId: "2026-08",
  keys: { "2026-08": env.DATAFN_ROUTING_KEY },
});
const replayStore = createMemoryDatafnRoutingReplayStore(); // tests and one-process deployments only

const placement = createConditionalKvDatafnPlacementDirectory(
  stores.atomicKv,
  { consistencyModel: "linearizable" },
);

const server = await createDatafnServer({
  schema,
  database: regionalDatabase,
  context: authenticateRequest,
  namespaceProvider: {
    getNamespace: (context) => context.authorizedNamespace,
  },
  plugins: [
    datafnMultiRegionPlugin({
      regionId: "eu-west",
      directory: permissionDirectory,
      placement: {
        directory: placement,
        requireRoutingAssertion: true,
        assertionVerifier: assertions,
        replayStore,
      },
    }),
  ],
});
```

The server derives the trusted namespace from authenticated context, verifies the gateway assertion, and checks region + epoch before plugin authorization, application authorization, or a database/sync operation. The built-in payload containment guard may reject internal-resource references before this placement check; it does not perform route or application authorization. Built-in HTTP, REST, sync, in-process search, public-link routes, and routed WebSocket handshakes use this fence. Health status remains cell-local and does not require a tenant placement.

Custom plugin routes must declare `meta.datafnPlacement.resolveNamespace`. The resolver either returns the authenticated namespace or an early `Response`. An undeclared custom route is rejected at startup in placement mode. Routes that are proven global and do not touch regional data may declare `datafnPlacement: "none"`.

## Canonical gateway

```ts
import {
  createDatafnGatewayRouter,
  withDatafnRoutingAssertion,
} from "@datafn/server";

const gateway = createDatafnGatewayRouter({
  directory: placement,
  deriveNamespace: async (request) =>
    (await authenticateRequest(request)).authorizedNamespace,
  cellRegistry: {
    resolve: ({ regionId, destinationRef }) =>
      internalCells.resolve(regionId, destinationRef),
  },
  assertionSigner: assertions,
  dispatcher: {
    // HTTP-origin example. Adapt this call when resolve() returns an RPC stub,
    // service binding, or function reference instead of a fetch-capable target.
    dispatch: ({ target, request, assertion }) =>
      target.fetch(withDatafnRoutingAssertion(request, assertion)),
  },
  maxCacheEntries: 10_000,
});
```

The gateway strips caller-supplied internal headers, preserves the method, complete path and query string, body, cookies, authorization, correlation/idempotency headers, and request ID, then signs namespace, region, epoch, method/request target, body presence and digest, audience, timestamps, and a nonce. It buffers and hashes at most 5 MiB before invoking even a body-reading namespace resolver, so resolver clones cannot accumulate an unbounded stream; set `maxBodyBytes` on the gateway and placement runtime when a deployment uses another limit. The placement cache also has an insertion-ordered bound (`maxCacheEntries`, default 10,000) in addition to its TTL. Each cell atomically consumes the signed nonce through a shared replay store before execution. Assertion-enabled placement configuration fails at startup unless it supplies both a verifier and replay store. The in-memory replay store is for tests and one-process deployments only; production cells sharing an audience need a bounded durable store with atomic first claim. The destination resolver may return an HTTP origin, service binding, RPC stub, or function reference, and the dispatcher must adapt the request for that target type; destination details are never serialized into a public response.

On an authenticated, guaranteed pre-execution `DATAFN_REGION_MISMATCH`, the gateway invalidates its cache, re-resolves placement, and retries exactly once. It does not replay ambiguous timeouts or responses produced after execution began. Existing mutation IDs and idempotency keys remain authoritative for application-level retries.

## Errors and availability

| Code | Meaning | Default behavior |
| --- | --- | --- |
| `DATAFN_PLACEMENT_NOT_FOUND` | No active placement or a tombstone | Fail closed; do not choose a default region |
| `DATAFN_PLACEMENT_UNAVAILABLE` | Directory read failed | Retryable 503; a miss is not inferred |
| `DATAFN_REGION_MISMATCH` | Wrong cell or stale epoch before execution | Internal metadata may trigger one gateway retry |
| `DATAFN_NAMESPACE_MOVING` | The move fence is active | Retryable 409; no cell accepts new work |
| `DATAFN_CELL_UNAVAILABLE` | Destination resolution or dispatch failed | Pre-send resolution failures are retryable; ambiguous dispatch failures report `executionStarted: true` and are not retry-safe |
| `DATAFN_ROUTING_ASSERTION_INVALID` | Spoofed, expired, or mismatched assertion | Non-retryable 401 |
| `DATAFN_ROUTING_RETRY_EXHAUSTED` | The bounded re-resolution was insufficient | Retryable 409; operator review may be required |
| `DATAFN_PAYLOAD_TOO_LARGE` | The gateway body limit was exceeded | Non-retryable 413 before dispatch |

Only a verified internal assertion receives region/epoch hints. Public direct responses do not reveal internal topology.

## WebSocket and sync epochs

Use `server.websocketHandler.addRoutedClient(client, authContext, handshakeRequest)` in placement mode. Routed clients must expose a transport-level `close` operation so fencing can deliver code `4510` before removing the session. The handshake pins namespace, region, and epoch. The legacy synchronous `addClient` rejects connections while placement mode is enabled so an adapter cannot accidentally bypass the fence.

When a move starts, call `fenceNamespace(namespace)` (or provide the new minimum epoch) on the source cell. Each fence advances a namespace generation, so a handshake that was still awaiting placement validation cannot register after the fence completes. Stale sessions close with code `4510` and reconnect through the canonical `wsUrl`. Mutation IDs, pull cursors, and reconcile checkpoints remain valid only if the migration copy/validation hooks preserve them; otherwise the application must fail explicitly and require a fresh clone.

## Migration protocol

Use `resolveNamespaceStoragePlan` from `@datafn/server` to copy, verify, fence, and drain every DataFn-owned namespace relation. Do not scan PostgreSQL catalogs or hard-code `__datafn_*` names in application code. See [Namespace storage contract](/docs/documentation/namespace-storage).

`migrateDatafnNamespace` implements the minimal fenced order:

1. CAS the active placement to `moving` at a newer epoch.
2. Quiesce source writes and close/fence old sessions.
3. Drain permission-directory outbox work.
4. Copy and validate tenant data, cursors, mutation IDs, and checkpoints.
5. Rebuild the permission projection and warm the target.
6. CAS the moving record to a target `active` placement with explicit `resume-target` recovery state at another epoch.
7. Resume target writes, then clear the recovery state through one final epoch CAS.

Failure before activation CASes to an active source placement with explicit `resume-source` recovery state. Gateway and cell traffic remain fenced until the required `rollbackSource` hook succeeds and a final epoch CAS clears that state; `migrateDatafnNamespace` rejects configurations without that hook before it fences writes. A failed or interrupted rollback can therefore be claimed and retried without publishing a quiesced source. The source rollback hook runs only if the first rollback CAS succeeds. A durable placement directory is required to persist the recovery owner, monotonic `recoveryFence`, and expiry lease across crashes; do not use the in-memory directory for migrations that must survive process restarts. After a crash, one retry claims the expired lease through CAS before continuing. Every external hook boundary must atomically compare and persist `recoveryFence` in the affected system, rejecting lower tokens before applying an effect; timer renewal alone cannot fence an already-running hook after takeover. `recoveryLeaseExpiresAt` is a live getter that reflects successful renewals, but it is scheduling guidance rather than a substitute for the fencing token. Hooks must remain idempotent. `resume-source` and `resume-target` placements remain fenced from gateway and cell traffic until their resume hook succeeds and the final CAS clears recovery state. Set `recoveryLeaseMs` longer than the maximum expected hook interval. A same-region destination-only change is rejected instead of silently ignoring it. Rollback after activation is another explicit migration; never edit a cache, region map, or DNS record out of band.

## Observability and operations

Provide `onEvent` to collect placement lookup/cache hit, forward, mismatch, retry, moving, directory unavailable, destination unavailable, epoch conflict, and assertion failure events. Hash namespace identifiers before sending them to shared telemetry. Monitor directory availability and latency, cross-region dispatch latency, retry exhaustion, assertion failures, permission-outbox backlog, and migration stalls.

Run shadow placement checks before enforcement, enable gateway routing for test tenants, and expand gradually. Keep the original single-region configuration as rollback only until the first placement move; after that, rollback must use the epoch protocol.
