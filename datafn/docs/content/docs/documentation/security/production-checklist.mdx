Don't ship DataFn to production without ticking every item below. They're independent — leaving any of them out can introduce a real vulnerability.

## Server configuration

- [ ] `authorize` requires a verified authenticated session for protected actions. Selector extraction does not authenticate callers.

- [ ] Resource gating in `authorize` uses `extractStructuralResourceSelectors` rather than reading `payload.resource` or recursively searching JSON.
- [ ] `allowUnknownResources` is `false` (the default — do not override).
- [ ] `debug` is `false` (set explicitly or rely on `NODE_ENV=production`).
- [ ] `limits.maxPayloadBytes` is set to a value appropriate for your records (default 5 MB is conservative).
- [ ] `limits.maxBatchSize` and `limits.maxTransactSteps` are reviewed against your client's behavior.
- [ ] `rateLimit.enabled` is `true` with per-endpoint caps; `keyExtractor` returns a user-id (not just IP) for authenticated apps.
- [ ] `redis` is configured if you run multiple server instances. Rate limit and sequence store both need it.

## Schema configuration

- [ ] Every resource has an explicit `permissions` block. Resources without `permissions` are denied by default.
- [ ] `permissions.read.fields` lists only fields safe to expose. System fields (`createdAt`, etc.) are included intentionally.
- [ ] `permissions.write.fields` lists only fields clients should be able to write.
- [ ] `idPrefix` is set per resource and is unique (no two resources share a prefix).
- [ ] Capability-managed fields (`createdAt`, `updatedAt`, `createdBy`, etc.) are never in `write.fields` (they're stripped anyway, but explicit is better).

## Multi-tenancy

- [ ] `namespaceProvider.getNamespace` returns a value derived from server-side context (session, not client input).
- [ ] `namespaceProvider.getActorId` is set if you want the `audit` capability to fill in `createdBy` / `updatedBy`.
- [ ] Cross-namespace operations (admin queries) run through a separate DataFn instance or a sentinel namespace gate — never through the same `authorize` callback.

## WebSocket

- [ ] Connections are authenticated **before** `addClient()` is called.
- [ ] `ws.maxConnections` and `ws.maxConnectionsPerNamespace` are set.
- [ ] `ws.heartbeatIntervalMs` and `ws.heartbeatTimeoutMs` are set (defaults are fine).
- [ ] Custom message types validate `namespace` against the auth context (or simply ignore namespace fields from clients).

## Data retention

- [ ] `retention.changeLogDays` is set. Unbounded growth degrades sync performance.
- [ ] `retention.idempotencyDays` is set. Idempotency cache rows accumulate quickly.
- [ ] `retention.pruneOnStartup` is `true` to clean up after a restart.

## Transport

- [ ] All traffic uses TLS. Terminate before DataFn (Caddy, Nginx, Cloudflare, your platform's edge).
- [ ] CORS allowlist is restrictive — only your frontend origins, not `*`.
- [ ] Cookies are `Secure`, `HttpOnly`, `SameSite=Lax` (or `Strict` if your auth flow allows).

## Observability

- [ ] `observability.timing` is on; `onTiming` writes to your metrics pipeline.
- [ ] `logger` is configured for JSON output in production.
- [ ] Rate-limit rejections (`httpStatus === 429`) are tracked.
- [ ] Authorization rejections (`error.code === "FORBIDDEN"`) are tracked and alerted on spikes.
- [ ] `INTERNAL` errors are alerted — they indicate unclassified server bugs.

## Backups

- [ ] Database backups run on a schedule (your platform — DataFn doesn't ship one).
- [ ] Restore is tested at least once per quarter.
- [ ] Backup encryption uses a key not stored in the same system (don't put the key in the same KMS that backs up that KMS).

## Dependencies

- [ ] DataFn versions across packages are aligned (`@datafn/server`, `@datafn/client`, `@datafn/core` should share major + minor).
- [ ] `npm audit` runs in CI; high-severity issues block deploys.
- [ ] Container base images are pinned and rebuilt weekly to pick up OS patches.

## Disaster recovery

- [ ] Graceful shutdown is configured (`shutdownTimeoutMs`).
- [ ] Health checks (`GET /datafn/status`) are wired to your load balancer.
- [ ] A documented runbook covers the top three failure modes: database failover, Redis failover, server restart loop.

## Going further

- [ ] Penetration test before public launch (or at least adversarial review by someone outside the team that built it).
- [ ] Bug bounty channel published in `SECURITY.md`.
- [ ] Quarterly review of the permissions policy against current product features.
